# Security: secrets, biometrics, sign-in

```rust
cx.spawn(async move |this, cx| {
    // Secrets: never in plain files, never synced or backed up.
    cx.secure_storage().set("refresh_token", &token).await?;
    let token = cx.secure_storage().get("refresh_token").await?;            // Option<String>
    cx.secure_storage().set_with("pin", "1234", SecureOptions::new().biometric()).await?;  // read = Face ID…
    cx.secure_storage().delete("pin").await?;

    // Is it the owner? Face ID, Touch ID, Optic ID, a fingerprint, then the passcode.
    match cx.authenticate("Unlock your notes").await {
        Ok(()) => unlock(),
        Err(DeviceError::Cancelled) => {}
        Err(e) => show(e),
    }
    let b = cx.biometry().await;            // kind (FaceId, Fingerprint…), enrolled, passcode, locked_out

    // Sign in with Apple, and OAuth 2 / OpenID Connect with PKCE (Google, Microsoft, Auth0, Keycloak…).
    let apple = cx.sign_in_with_apple(AppleSignIn::new().email().full_name()).await?;
    let tokens = prism::oauth::OAuth::google("1234-abc.apps.googleusercontent.com").sign_in(&cx).await?;
    let email = tokens.id_claims().and_then(|c| c["email"].as_str().map(String::from));

    // A self-hosted OAuth 2 server: metadata (RFC 8414 or OpenID), and a client registered once (RFC 7591).
    let server = OAuth::server("https://git.example.com", "").dynamic_registration("My App").scope("read");
    let server = server.resolve(&cx).await?;     // endpoints + client id: keep it
    let tokens = server.sign_in(&cx).await?;
    // Later, on any thread (a blocking API client after a 401):
    // server.refresh_blocking(&refresh_token)?
    // Signing out: the server forgets the refresh token (RFC 7009).
    server.revoke(&cx, &refresh_token, Some(TokenTypeHint::RefreshToken)).await?;
});
```

- **Biometric secrets** need the owner every time they are read; new fingers or faces make them unreadable (Apple, Android), and so does resetting Windows Hello: store them again. Setting one never prompts, except on Windows (below) and the first one in a browser on the web (below). `biometric()` means the system itself checks the owner (Keychain access control, the Android Keystore, the server on the web, a Windows Hello key): where it cannot (the Linux Secret Service, the macOS login keychain of an app without a provisioning profile, Windows without Hello set up), `set_with` fails with `Unavailable` and the previous secret stays. `confirm_owner()` is the same on Apple platforms with a provisioning profile, Android and the web; on Windows and Linux (and macOS without a profile) the value is stored as it is and Prism asks for the owner (Windows Hello, fprintd, Touch ID) before handing it to the app; the store does not check, so another program of the same user that reads it gets the value without a prompt. Use it when that is enough for the secret, and handle `Unavailable` for `biometric()`.
- **Windows biometric secrets**: each app has one Windows Hello key (`KeyCredentialManager`, named `Prism/<app>/secure-storage`, in the TPM where there is one), which signs only after Hello's own prompt (face, fingerprint or Hello PIN). Storing a secret draws a random challenge for the key to sign; Hello signs with RSA PKCS#1 v1.5, which is deterministic, so only that key gives the same signature again. HKDF-SHA256 turns the signature into an AES-256-GCM key; Credential Manager keeps the challenge and the sealed value (bound to the app and the secret's name), never the key. Reading has the key sign the challenge again. Nothing is stored unless every step succeeded, so a cancelled prompt keeps the previous secret. The prompt is Windows' own: `get_with_prompt`'s text is not shown there. Another program of the same user can ask the same key for a signature, but Windows then shows Hello's prompt. Resetting Hello (a new PIN after « I forgot my PIN ») deletes the key: reading fails with `Failed`, and the app stores the secret again.
- **No biometric secrets on Linux**, by decision: no desktop store ties a secret to the user's presence. The Secret Service unlocks a whole collection at login, after which every program of the user reads it. The kernel keyring checks no presence. The TPM (`/dev/tpmrm0`) is closed to users on most distributions, and its PIN would be typed into the app, not into a prompt of the system. fprintd and polkit only answer yes or no to the app, and nothing binds that answer to the secret, which is what `confirm_owner()` does already. So `biometric()` answers `Unavailable` there.
- **Simulators** need no provisioning profile for `secure_storage`: `prism` gives simulator builds the `application-identifier` entitlement, which the keychain uses as the app's access group ([iOS](../platforms/ios.md)).
- **Face ID** needs a usage text: `face_id = "…"` under `[permissions]` in Prism.toml (`NSFaceIDUsageDescription`). Without it the call fails with a message saying so instead of crashing.
- **Passkeys in the field's suggestions** (#203): `cx.webauthn_autofill(options)` starts a sign-in the user finishes by picking a passkey in the suggestions of the username field, without a sheet (« conditional mediation »). Mark the field `text_input().attr("autocomplete", "username webauthn")` and start it as the sign-in screen appears, with the server's request options (no `allowCredentials`); it answers the assertion JSON like `webauthn_get`. Any other ceremony replaces it (it then answers `Err(Cancelled)`: start it again if the screen stays). Web: `navigator.credentials.get({ mediation: "conditional" })` where the browser has it; iOS, iPadOS, visionOS: `performAutoFillAssistedRequests`, the field getting `textContentType = .username` from its `autocomplete` (also `current-password`, `new-password`, `one-time-code`, `email`, `name`, `tel`, `postal-code`, `url`). `Err(Unavailable)` on macOS, Android, Linux, Windows and older browsers: keep a « Sign in with a passkey » button calling `webauthn_get`.
- **Passkeys on Apple platforms** need the relying party's domain as a `webcredentials:` associated domain: `[ios] associated_domains = ["webcredentials:example.com"]` (#191) writes it into the signed entitlements when the provisioning profile has the Associated Domains capability (a note says so otherwise), and the domain serves `/.well-known/apple-app-site-association` listing the app. `applinks:` entries give universal links. The simulator gets them too; on macOS only App Store builds can carry them. Android needs no app setting: the domain's `/.well-known/assetlinks.json` names the app.
- **Sign in with Apple** needs the `com.apple.developer.applesignin` entitlement: `[ios] sign_in_with_apple = true` takes it from the provisioning profile (enable the capability for the App ID). `capabilities().sign_in_with_apple` is true only in bundles built with it. Verify `identity_token` (or exchange `authorization_code`) on your server: Apple's signature, `iss` `https://appleid.apple.com`, `aud` your bundle id, `exp`, and the `nonce` claim, which is the SHA-256 (lower-case hex) of the nonce you gave `AppleSignIn::nonce` (Prism hashes it, so pass the nonce your server handed out, unhashed). A credential whose `state` is not the request's is refused.
- **Redirect URI** on iOS, iPadOS, visionOS, macOS, watchOS, tvOS and Android: `prism-<package>:/oauth`, where `<package>` is the cargo package name (`[app] package` in `Prism.toml`, else `Cargo.toml`'s `[package] name`) with `_` written `-`. It is neither the display name nor the bundle id. A package `my_dashboard` (bundle id `com.example.dashboard`, name "My Dashboard") registers exactly `prism-my-dashboard:/oauth` with the provider. `.redirect_uri(…)` with a custom scheme the app receives replaces it; `OAuth::google` uses Google's reversed client id on Apple.
- **OAuth**: authorization code + PKCE (S256), random `state` checked on return. The sign-in ends only with a redirect to exactly its redirect URI (scheme, host, port and path) carrying its `state` once: on Linux, Windows and Android other requests and deep links to it (a favicon, another attempt's callback, one sent by another app) are refused and the sign-in keeps waiting; on the web the server hands each callback to the sign-in with its `state`. With the `openid` scope the token endpoint must return an ID token, and Prism checks it: a signing algorithm (not `none`), the issuer, the audience (and `azp` when there are several), the expiry (five minutes' clock skew), a subject and the sign-in's `nonce`; refreshed ID tokens too. Not its signature: it comes straight from the token endpoint over HTTPS, which OpenID Connect accepts instead (Core §3.1.3.7); verify it with the provider's keys before trusting it on your server. `Tokens::id_claims` decodes it for display. Public clients only on devices (no secret); `.code_only()` hands the code and verifier to your server instead. `OAuth::oidc(issuer, client_id)` and `OAuth::server(issuer, client_id)` (plain OAuth 2, no `openid` scope) discover the endpoints.
- **Logs**: printing (`{:?}`) a `prism::http` `Request`, `Response` or `ResponseHead`, an `OAuth`, `Tokens`, `Registration` or `Pkce`, an `AppleCredential`, a `PushSubscription` or `ActivityPushToken`, or a `prism_push` `Subscription`, `Keys` or `HttpRequest` shows no secret: tokens, keys and client secrets show as `<redacted>` (or `Some(<redacted>)`), header values only for harmless headers (`Content-Type`, `Accept`…), bodies by size, URLs without their query (push URLs by origin). Read the fields themselves when you need the values. HTTP error messages leave the URL's query out, and a push service's refusal (`PushError::Rejected`) keeps at most 1 KiB of its answer, on one line, without the subscription's endpoint.
- **Discovery** tries RFC 8414 metadata (`/.well-known/oauth-authorization-server`, inserted between the host and the issuer's path: `https://h/.well-known/oauth-authorization-server/realm`) and OpenID Connect discovery (`<issuer>/.well-known/openid-configuration`), OpenID first when the scopes include `openid`, then the OpenID document with the path inserted (RFC 8414 §5). A document without an `issuer`, or another issuer's, is refused (mix-up attacks).
- **Transport**: the issuer and every endpoint must use HTTPS; plain HTTP is accepted only for `localhost`, `127.0.0.1` and `[::1]` (a test provider such as `scripts/mock-oidc.py`; on the Android emulator, `adb reverse tcp:8765 tcp:8765` reaches the computer's). Token, refresh, revocation and registration requests follow no redirect (a redirect is an error, so credentials never reach another server), and metadata and endpoint answers are capped at 1 MiB. `discovery_urls(issuer, oidc_first)` lists them; `discover_blocking()` and `apply_metadata()` are public.
- **Dynamic client registration** (RFC 7591): with an empty client id and `.dynamic_registration("My App")`, the first sign-in posts to the server's `registration_endpoint` (discovered) a public client: `client_name`, this platform's redirect URI, `grant_types` `authorization_code` and `refresh_token`, `response_types` `code`, `token_endpoint_auth_method: none`, `application_type` `native` (custom scheme or loopback) or `web`. `.registration_token(t)` sends an initial access token. The answer is kept in secure storage (per issuer and client name), so the app registers once per device, and again when the redirect URI changes (a loopback redirect matches on any port, RFC 8252 §7.3), when a returned secret expires, or after the server answers `invalid_client`. If the server issues a `client_secret` anyway, it is stored with the id and sent as it asks (`client_secret_basic` or `client_secret_post`); a per-install secret is not a shipped secret. Without secure storage the app registers at each launch. On the web, registrations are per browser (the server-side store). `register_blocking`, `registration_request`, `parse_registration_response` and `Registration` are there for code that manages it itself.
- **Refreshing on any thread**: `resolve(&cx)` returns the provider with its endpoints and client id; keep it, and `refresh_blocking(refresh_token)` works from any thread (like `Request::send_blocking`), sharing the token request (`token_request`, public) with `sign_in` and `refresh`. The refresh token is kept unless the server rotates it. Google requires the reversed client id as the scheme for iOS clients (`OAuth::google` does it on Apple); for Android it only accepts App Links or Credential Manager (Play services), so use a provider that allows custom schemes, or bounce through your server.
- **Signing out** (RFC 7009): `revoke(&cx, token, hint)` (or `revoke_blocking(token, hint)` on any thread) posts the token, its `token_type_hint` (`TokenTypeHint::RefreshToken` or `AccessToken`, optional) and the client's credentials to the server's `revocation_endpoint`, read from its metadata (kept in `revocation_url`; `OAuth::google` knows Google's). Revoking the refresh token usually ends its access tokens too. A token the server does not know is not an error (RFC 7009 answers 200 either way); a server without a revocation endpoint is. `revocation_request` and `parse_revocation_response` are public, like the token request.
- **Web secrets** are a server-side store, because the app runs there: the browser never sees them. Set `PRISM_SECRET_KEY` (64 hex digits) in production; otherwise the first worker to need one generates a key in the data directory (`.secret-key`), and every worker sharing that directory uses it. A `PRISM_SECRET_KEY` that is not 64 hex digits, or a key file that holds no key, makes `secure_storage` calls fail instead of sealing secrets with another key. Secret files and their directories are created readable by the server's user only (`0600`/`0700` on Unix; on Windows they inherit the data directory's ACL). A write or delete that fails returns `Err`. WebAuthn needs a secure context (`https://` or `localhost`); the first `authenticate`, or the first biometric secret stored, enrolls this browser's platform credential (a WebAuthn prompt; `Err(Unavailable)` without a platform authenticator). Once enrolled, every later check is an assertion by that credential: the page cannot answer with a new registration to replace it, and a biometric secret is never read through an enrollment. Enrollment trusts the session it happens in: call `authenticate` right after the user signs in if the gate must belong to that user. When a popup or WebAuthn needs a fresh tap (Safari), the page shows a "Continue" button.
- **Loopback redirects** (Linux, Windows): `auth_redirect` gives the URI of one listener on `127.0.0.1`, which the next `web_auth` takes; asked again before that (`resolve` checks a registration, then `sign_in` asks), it gives the same one. A listener no sign-in takes closes after 10 minutes, so `resolve` and `refresh` leave no socket open. Two sign-ins that both ask before either opens the browser share the URI, and the second to open it fails: start them one after the other.
- **Web sign-in popups**: the provider's redirect reaches `<base>/_prism/auth/callback`, which hands it to the session that opened the popup, by its `state`, once. Only that redirect completes `web_auth`: the page can cancel it (the popup was closed or blocked), not answer it. A popup has 10 minutes to come back, a session may have 8 waiting at once (a ninth fails), and the ones a session leaves open end with it.
- **Web session cookies**: a handler signing a user in sets the host's session cookie with `cx.set_cookie(Cookie::new("session", token))` (`HttpOnly; Secure; SameSite=Lax` by default), through a one-time ticket the page redeems at `<base>/_prism/cookie`, then calls `cx.reconnect()` so the host's middleware sees it ([Web](../platforms/web.md), "Cookies from a handler"). Natively, keep the token in secure storage instead: `set_cookie` answers `Unavailable` there.
- **Web browser id**: signing in gives the browser a new id and moves its data there, so an id someone planted before opens nothing ([Web](../platforms/web.md), "A sign-in renews it"). `prism::oauth` (through `cx.web_auth`) and `cx.webauthn_get` / `webauthn_create` / `webauthn_autofill` do it for you; an app with its own sign-in (a password, a magic link) calls `cx.renew_browser_id().await?` before storing what proves it. Natively it answers `Ok(())` at once.
- **Passkeys of your own server** (#94): `authenticate` uses Prism's own credential to unlock secrets on this device. To sign users in with passkeys of your app's relying party (or add a passkey to an account), run the ceremony with the options your server produced and send the result back to it:

  ```rust
  // `server` is your app's own API client.
  let options = server.start_passkey_registration().await?;   // PublicKeyCredentialCreationOptionsJSON
  let credential = cx.webauthn_create(options).await?;        // RegistrationResponseJSON
  server.finish_passkey_registration(credential).await?;

  let options = server.start_passkey_sign_in().await?;        // PublicKeyCredentialRequestOptionsJSON
  let assertion = cx.webauthn_get(options).await?;            // AuthenticationResponseJSON
  server.finish_passkey_sign_in(assertion).await?;
  ```

  Options and answers are the WebAuthn JSON forms (binary fields in base64url, what server libraries produce and `PublicKeyCredential.toJSON()` gives); a `{"publicKey": …}` wrapper is accepted. Prism only runs the ceremony: your server checks the challenge, origin and signature. `Err(Cancelled)` when the user declines, `Err(Unavailable)` where there are no passkeys (`capabilities().passkeys`). Errors the platform names come back as `DeviceError::Platform { name, message }` (#189), with the web's `DOMException` names on every platform: `e.name() == Some("InvalidStateError")` when registering a passkey this device already holds (an `excludeCredentials` match: the web's `InvalidStateError`, Apple's `matchedExcludedCredential`, Android's invalid-state DOM exception). Match on the name, never on the message, which depends on the browser, the OS and the language.

  | | Ceremony | Needs |
  |---|---|---|
  | Web | `navigator.credentials.create` / `get` in the page (a « Continue » tap when the browser wants a fresh gesture) | the page's origin under the relying party id |
  | macOS, iOS, iPadOS, visionOS, tvOS | `ASAuthorizationPlatformPublicKeyCredentialProvider` | the relying party's domain as a `webcredentials:` associated domain of the app (apple-app-site-association) |
  | Android 14+ | the Credential Manager (`android.credentials`) | the app in the domain's Digital Asset Links |
  | Linux, Windows, watchOS, older Android | — (`Unavailable`) | |
- **Biometrics only** (`AuthRequest::biometrics_only()`): where the system's owner check may accept a PIN or password without saying so (WebAuthn on the web, Windows Hello, watchOS), the request fails with `Unavailable`; ask with the passcode fallback (`AuthRequest::new`) there. Apple's other platforms, Android and Linux (fprintd) limit the check to biometrics.
- **Linux** has no desktop standard for checking a password on behalf of an app (polkit authorizes system actions, not apps): `authenticate` uses fprintd, otherwise `Unavailable`. Biometric secrets are checked by the app with fprintd before the keyring hands them out.
- <a id="widget-buttons"></a>**Widget buttons on macOS** (`div().widget_action(..)`): a macOS widget cannot run the app's code, so a tap opens the app on a link (`/__prism/widget-action?kind=…&action=…&payload=…&token=…`), and any app or web page can open the same link. A link runs its action only when it is signed, on screen and unused. *Signed*: its token is the id of the drawing of the widgets it belongs to (every reload draws them anew, with a new id) and an HMAC-SHA256 under the app's key (`widget-link-key`, 32 random bytes, `0600`, in the app's data directory) of that id and the action (kind, action, payload, length-prefixed), truncated to 128 bits. *On screen*: its drawing is the current one, or one the app replaced less than an hour ago. *Unused*: the ledger next to the key (`widget-link-ledger`) records each link that ran, and the app reads it again before every check, so a second instance of the app cannot run the link either. A replayed link (from a log, or another app that claimed the URL scheme), or one whose drawing expired, runs nothing and redraws the widgets; a forged one does nothing. Why this design: a widget timeline lasts until the app reloads it, so a button may be tapped days after it was drawn, by a tap that launches the app, and that first tap must work: a fixed expiry in the token would break it, so links expire with their drawing instead. One long-term key with public drawing ids binds the links to their drawing as well as a key per drawing would, with no secret in the ledger. And because the MAC makes the issued links implicit, the ledger holds only what was tapped, not every button of every size, configuration and drawing ahead (what single-use random nonces would need). What is left: a link nobody opened yet runs once, while its drawing is on screen, for whoever gets it first. That takes copying it out of the widget's files (the user's own file access, which reads the key too) or another app catching the tap by claiming the URL scheme, and it runs only the action the button shows. iOS, visionOS and Android do not use links: the button is an App Intent hidden from Shortcuts, or a broadcast to a receiver no other app can reach, so only the system's widget host delivers a tap, and an action link never runs anything there. Handlers should still check anything that must happen only once (a payment): a link runs once, but the user can tap the next drawing's button again.
